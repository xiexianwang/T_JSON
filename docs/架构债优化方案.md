架构债优化方案
当前代码已完成第一阶段 MVP 按钮迁移，但仍有几个高风险问题。建议不要先拆大文件，而是按“生命周期安全 → 多设备正确性 → 状态数据流 → 分层解耦 → 基础设施拆分 → 测试建设”的顺序推进。
一、当前架构债盘点
P0：设备生命周期和线程退出风险
涉及：
- src/service/DeviceManager.cpp
- src/service/DeviceContext.cpp
- src/infrastructure/rtspthread.cpp
问题：
- DeviceManager::removeDevice() 和 removeAllDevices() 使用 deleteLater()，但没有确认对象已经销毁。
- DeviceContext::stopConnection() 未完整关闭电机 TCP、PTZ 转发器和所有定时器。
- RtspThread::closeStream() 的注释说“等待线程退出”，但实际没有明确 wait() 保证。
- RTSP 关闭、重开、析构之间存在竞态。
- RtspThread 的 m_stop、m_url、m_connecting 存在加锁不一致问题。
风险：
- 程序退出时后台线程仍运行。
- 重连过程中关闭程序可能崩溃。
- 重新打开视频流时旧线程和新线程同时工作。
- DLL、Socket、FFmpeg 资源释放不完整。
P0：多设备逻辑尚未真正闭环
涉及：
- src/ui/views/mainwindow.cpp
- src/ui/main/MainPresenter.cpp
- src/ui/components/VideoGridWidget.*
- src/service/DeviceManager.*
问题：
- 多处仍硬编码 "default_device"。
- 当前设备 ID 与视频控件、控制指令、状态刷新没有统一绑定。
- 部分退出、视频关闭、框选、RTSP 错误处理仍以默认设备为目标。
- 电机信号目前主要绑定默认设备。
- DeviceContext 虽然维护了设备状态，但 Presenter/UI 不完全以当前设备状态为唯一来源。
风险：
- 切换设备后 PTZ 或镜头指令发给错误设备。
- 视频和仪表盘显示设备状态不一致。
- 某设备断开时误修改默认设备 UI。
P1：Presenter 与 View 仍然高度耦合
MainPresenter.cpp 目前仍直接操作：
- MainWindow
- Ui::MainWindow
- VideoGridWidget
- MapWidget
- 控件文本、按钮状态和弹窗
- MainWindow::requireConnected()
- MainWindow::refreshStyle()
- MainWindow::calcVisualDistance()
这与当前文档中“哑巴 View”的目标不一致。当前实际模式更接近：
MainWindow + MainPresenter 互相操作
而不是：
MainWindow 事件/展示
        ↓
MainPresenter 业务协调
        ↓
DeviceContext / EventBus
P1：状态模型和 JSON 事件存在重复数据源
当前同时存在：
TJsonClient::jsonReceived
        ↓
MainPresenter 再次解析 JSON
以及：
TJsonClient::jsonReceived
        ↓
DeviceContext 更新 DeviceState
        ↓
EventBus::sigDeviceStateUpdated
问题：
- DeviceState 已存在，但没有成为 UI 的主要状态来源。
- JSON 可能被重复解析。
- Presenter 仍然依赖完整原始 JSON。
- UI 状态可能与 DeviceContext::m_state 不一致。
- AI 超时只通知 UI，没有完整更新状态快照。
P1：TJsonClient 职责过重
TJsonClient 同时负责：
- TCP 连接
- 自动重连
- 心跳
- 标准帧解析
- 抓拍帧解析
- JSON 解析
- ACK 处理
- 串口透传封装
此外还存在：
- 错误 JSON 主要只写日志，没有统一错误事件。
- ACK 状态类型存在 quint16 到 quint8 的收窄风险。
- 不同帧类型的载荷解析边界不够清晰。
- 已连接或正在连接时重复调用 connectToHost() 的保护不足。
P2：DeviceContext 暴露底层组件
DeviceContext 仍公开：
tcpClient()
motorController()
videoStream()
ptzForwarder()
虽然 MainPresenter 的访问器已经私有化，但底层对象仍可以继续从业务层向外泄漏。长期目标应改为只公开设备业务能力：
connectDevice()
disconnectDevice()
movePtz()
moveLens()
startVideo()
stopVideo()
setMotorMode()
currentState()
P2：DeviceController 职责过重
DeviceController 同时承担：
- Pelco-D
- VISCA
- MODBUS-RTU
- STM32-TCP
- 串口通信
- TCP 通信
- 透传
- 电机状态
- 设备业务命令
并且 sendMotorTcpV4() 使用了：
waitForConnected(500)
这可能阻塞 UI 线程。
P2：EventBus 是全局同步广播
当前问题：
- 单例永久存在。
- 事件订阅缺少明确生命周期。
- 高频 QImage、JSON 通过全局总线传播，可能产生复制和 UI 压力。
- 事件数量较多，部分事件没有实际调用方。
- Presenter 重复创建时需要防止重复连接。
P3：超大文件
当前约：
- mainwindow.cpp：1386 行
- MainPresenter.cpp：1349 行
其中混合了：
- 控件初始化
- 业务命令
- 状态转换
- 地图逻辑
- 视频逻辑
- 设备切换
- 弹窗和提示
- 地理计算
不建议第一步直接拆文件。应先完成职责边界收敛，再按稳定边界拆分。
P3：测试和构建体系不足
当前：
- 没有 enable_testing()。
- 没有 add_test()。
- 没有协议解析单元测试。
- 没有模拟设备或本地 TCP 测试目标。
- 没有 RTSP 生命周期测试。
- windeployqt6.exe 的存在检查与实际调用名称需要统一确认。
- thirdparty/aws-sdk-cpp 仍存在大量无效依赖，且当前工作树仍显示其子模块有外部改动。
文档状态债
代码已经提交，但文档仍有旧状态：
- ARCHITECTURE.md 仍写着“未提交改动”。
- docs/CHANGELOG.md 仍写着本次改动“未提交”。
这属于低风险、应立即清理的文档债。
二、推荐实施路线
阶段 0：文档和基线整理
目标：先让架构事实与代码一致。
内容：
1. 更新 ARCHITECTURE.md §8。
2. 更新 docs/CHANGELOG.md 中“改动未提交”的旧描述。
3. 明确 thirdparty/aws-sdk-cpp 是否属于外部已有改动，不纳入本轮。
4. 固定本轮优化前基线：
- Debug 构建通过。
- 记录当前提交号。
- 保存 git status。
- 增加静态检查命令。
验收：
- 文档不再错误描述已提交改动。
- 现有构建保持通过。
- 不修改 AWS 子模块状态。
阶段 1：设备生命周期和 RTSP 安全
优先级最高，建议首先实施。
1.1 明确停止协议
为 DeviceContext 增加统一停止流程：
void stop();
bool isStopped() const;
停止顺序建议：
停止自动重连
停止定时器
停止 PTZ 转发
关闭电机 TCP
关闭电机串口
关闭 RTSP 并等待线程结束
断开 TJsonClient
1.2 修正 RtspThread
目标：
- closeStream() 必须保证线程退出后返回。
- 所有共享状态统一通过 QMutex 或原子变量访问。
- 禁止旧线程未结束时再次启动。
- 用户主动关闭后不得自动重连。
- openStream() 应明确覆盖旧 URL 的行为。
建议接口：
bool openStream(const QString& url);
bool closeStream(int timeoutMs = 3000);
bool isRunningSafely() const;
1.3 修正 DeviceManager
建议：
- removeDevice() 先同步停止，再销毁对象。
- removeAllDevices() 使用统一销毁路径。
- 明确 DeviceContext 的所有权。
- 不再依赖 deleteLater() 后立即清空就认为资源已释放。
验收：
- 连续打开/关闭 RTSP 100 次无崩溃。
- 退出程序时所有 QThread 已结束。
- 断流重连时主动关闭不会再次重连。
- 设备删除后重新添加同 ID 不会收到旧设备信号。
阶段 2：消除默认设备硬编码
目标：让多设备逻辑真正可用。
2.1 统一当前设备入口
所有 UI 相关操作统一使用：
QString MainPresenter::currentDeviceId() const;
DeviceContext* MainPresenter::currentDevice() const;
禁止在业务代码中出现：
"default_device"
初始化阶段可以保留默认设备配置，但不能作为后续业务目标。
2.2 给视频控件绑定设备 ID
VideoGridWidget 和 VideoWidget 的帧更新、框选、RTSP 错误都必须带 deviceId：
void frameReady(const QString& deviceId, const QImage& frame);
void streamError(const QString& deviceId, const QString& message);
2.3 设备切换时统一刷新
设备切换应成为一个完整事务：
更新 currentDeviceId
切换视频控件
刷新 DeviceState
刷新 PTZ/镜头/AI/地图
刷新按钮可用状态
刷新连接状态
验收：
- 两台设备同时连接时，PTZ 指令目标正确。
- 切换当前设备后镜头控制目标正确。
- 当前设备断开不会清空其他设备视频。
- 框选跟踪发送到当前设备，而不是默认设备。
阶段 3：收敛状态数据流
目标：让 DeviceState 成为唯一的业务状态来源。
3.1 Presenter 订阅结构化事件
优先使用：
sigDeviceStateUpdated
sigDeviceAiInfoUpdated
sigDeviceFrameReady
sigDeviceConnected
sigDeviceDisconnected
逐步减少：
sigJsonReceived
在 UI 业务中的使用。
3.2 扩展状态模型
DeviceState 建议覆盖：
- 连接状态
- PTZ 状态
- 镜头状态
- 图像参数
- AI 状态
- 目标列表
- RTSP 状态
- 电机状态
- 最近错误
- 最近 ACK
3.3 区分原始数据和业务快照
建议：
TJsonClient：输出原始协议事件
DeviceContext：解析并更新 DeviceState
Presenter：消费结构化状态
View：只展示 Presenter 推送的数据
原始 JSON 仅保留给：
- 调试日志
- 未知协议兼容
- 协议分析
验收：
- 同一状态帧不再被 Presenter 重复解析。
- UI 只根据结构化状态更新。
- AI 超时会同步更新状态模型。
- 状态变化可用单元测试验证。
阶段 4：收敛 Presenter/View 边界
目标：Presenter 不再直接操作 Ui::MainWindow。
4.1 增加窄 View 接口
可以先定义接口，而不是一次性重写所有 UI：
class IMainView {
public:
    virtual ~IMainView() = default;

    virtual void showConnectionState(...) = 0;
    virtual void showDeviceState(...) = 0;
    virtual void showAiTargets(...) = 0;
    virtual void showError(...) = 0;
    virtual void updateControlAvailability(...) = 0;
};
MainWindow 实现该接口，Presenter 只依赖 IMainView。
4.2 将计算逻辑下沉
以下逻辑不应放在 MainWindow：
- 地理距离计算
- 目标坐标转换
- AI 状态机
- PTZ 控制状态判断
- 当前设备状态转换
建议放入：
- core/GeoCalculator
- core/TrackingState
- service/DeviceContext
- service/DeviceCommandService
4.3 Presenter 改为发布 ViewModel
更稳妥的中间形态：
struct MainViewState {
    QString deviceId;
    bool connected;
    bool videoRunning;
    PtzState ptz;
    LensState lens;
    AiState ai;
};
Presenter 产生 MainViewState，View 负责渲染。
验收：
- MainPresenter.cpp 不再 include ui_mainwindow.h。
- Presenter 不再调用 ui->xxx。
- Presenter 不再调用 MainWindow 具体控件方法。
- MainWindow 只保留布局、信号连接和展示逻辑。
阶段 5：拆分基础设施
5.1 拆分 TJsonClient
建议新增：
TJsonFrameCodec
TJsonProtocolParser
TJsonClient
职责：
- TJsonFrameCodec：帧头、长度、粘包、半包、重同步。
- TJsonProtocolParser：按帧类型解析 JSON、ACK、抓拍。
- TJsonClient：Socket、连接、重连、心跳。
5.2 拆分 DeviceController
建议拆成：
DeviceCommandService
PelcoDProtocol
ViscaProtocol
ModbusTransport
Stm32TcpTransport
DeviceController 最终只做协议选择和业务编排。
5.3 封装 DeviceContext
最终禁止公开：
tcpClient()
motorController()
videoStream()
ptzForwarder()
只公开设备业务 API 和状态：
connectDevice()
disconnectDevice()
startVideo()
stopVideo()
movePtz()
moveLens()
setWorkMode()
setAlgorithm()
currentState()
阶段 6：测试与构建体系
建议使用 Qt Test，建立：
tests/
├── CMakeLists.txt
├── test_tjsonframecodec.cpp
├── test_jsonframeparser.cpp
├── test_protocolbuilder.cpp
├── test_devicestate.cpp
└── test_devicecontext.cpp
优先测试：
- 粘包和半包。
- 非法帧头。
- 非法长度。
- ACK 状态码。
- 抓拍帧边界。
- Pelco-D checksum。
- DeviceState 更新。
- RTSP 关闭和重连状态机。
- 多设备当前设备切换。
CMake 增加：
include(CTest)
enable_testing()
并单独创建测试目标，避免测试依赖 WebEngine 和 FFmpeg 时过重。
